# TrevioKit

Private inventory, retailer transactions and expenses workspace built with **Next.js App Router, TypeScript and MongoDB Atlas Free (M0)**. Prepared for Vercel; **not deployed**. MongoDB stores business data permanently. The disposable local preview is only for manual testing.

## Features

| Sidebar page | What it provides |
| --- | --- |
| Dashboard | Date-filtered net revenue, payments, units sold/returned, charts and recent activity; current due and stock across all dates. |
| Inventory | Separate stock per product/size, selling price, optional HTTPS image URL, search/archive, initial quantity, total stock row. Add product opens a form; Edit opens product editing and stock adjustment. |
| New Sale / Exchange | Required retailer, multiple product lines, adjustable selling prices, original-price returns, combined exchanges, partial payments and settlement of previous due. |
| Retailers | Name/phone and optional shop/address; click a retailer for all invoices, units sold/returned, total payments and current due/credit. |
| Sales / Invoices | Search invoice number, retailer or shop; filter retailer and custom dates; units, paid amount, payment status and printable invoices. |
| Expenses | Add description, positive amount and expense date; date-filtered history, record count and total spending. |
| Analysis | Date-filtered revenue, payments, expenses, revenue after expenses, unit trends, expense charts, top products/sizes and retailers. |

Dashboard, Expenses and Analysis offer **All, Today, Last 7 days, Last 30 days and Custom range**. Dates use Asia/Dhaka; custom endpoints are inclusive. Sales use transaction dates; expenses use their expense dates, including backdated entries. Analysis totals cover all matching records; rankings show the top 10 and charts show the latest 60 active days or 24 active months. Revenue after expenses excludes product costs and is not profit.

The workspace uses the Soft Forest palette and responsive layouts. Tables are centered and compact. Printable invoices use a separate black-and-white A4 layout.

## Local setup with Atlas

1. Install Node.js **24.x** and npm. If using nvm, run `nvm use` (the repository includes `.nvmrc`). Run `npm ci`.
2. Create an Atlas Free cluster using the steps below. Use a separate development database and database user.
3. Copy the example locally:

   ```sh
   cp .env.example .env.local
   ```

4. Open `.env.local` in your editor and fill in the variables below. Enter credentials locally; never paste them into chat or commit them.
5. Run `npm run owner:hash` in an interactive terminal. Enter your chosen owner password privately (12–256 characters). Paste the generated salted hash into `OWNER_PASSWORD_HASH`. Sign in with the original password, not the hash.
6. Generate a session secret locally:

   ```sh
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```

   Paste the result into `SESSION_SECRET`.
7. Run `npm run dev`, visit **http://localhost:3000**, and sign in with your configured owner username and password. Restart the server after changing environment variables. There is no built-in production/test owner account in this mode.

| Environment variable | Required value |
| --- | --- |
| `MONGODB_URI` | Atlas Node.js driver connection string, with database credentials and URL-encoded special characters. |
| `MONGODB_DB` | Database name, e.g. `treviokit_dev` locally and `treviokit` in production. |
| `OWNER_USERNAME` | Your one owner login name. |
| `OWNER_PASSWORD_HASH` | Exact `salt:hash` value generated by `npm run owner:hash`. |
| `SESSION_SECRET` | Random 64-character hexadecimal secret from the command above. Use a fresh production secret. |
| `APP_ORIGIN` | Exact allowed browser origin: `http://localhost:3000` locally; your final `https://...` domain on Vercel, with no path. |

All six variables are server-only. Do not add `NEXT_PUBLIC_` prefixes. `.env.example` contains placeholders only. `.env.local`, Vercel metadata, build output, logs and backups are excluded from Git.

```sh
npm run build

```

The production build must precede integration tests. Unit tests cover money, input validation, date filters and balances. Integration tests use isolated local MongoDB replica sets and a production HTTP server to check atomic rollback, overselling, excessive returns, duplicate submissions, original-price credits, sequential invoice numbers, combined payments, cleared statuses, expenses, analysis and owner access. They do not connect to Atlas or insert real business data. First use may download MongoDB; allow local ports, including 3108.

## MongoDB Atlas setup

1. Create/sign in to an account at [MongoDB Atlas](https://www.mongodb.com/cloud/atlas), create a project and select a **Free / M0** cluster. Choose a region near your users and Vercel region. Avoid loading sample data into the business database.
2. In Database Access, create a dedicated database user, separate from your Atlas account, with read/write access only to the TrevioKit database. Use a generated strong password. Keep development and production credentials separate.
3. In Network Access, allow your local public IP for development. Production must allow Vercel function outbound connections. Prefer restricted egress through a Vercel plan/network configuration with stable outbound IPs where available. If using Atlas's broad `0.0.0.0/0` access option, understand that this exposes network reachability: retain TLS, a strong narrowly scoped database user and credential rotation. Remove obsolete local IP entries.
4. Choose Connect → Drivers → Node.js and copy the `mongodb+srv://…` connection string. URL-encode special characters in the username/password. Set `MONGODB_URI` only in `.env.local` and Vercel server environment settings. Set `MONGODB_DB=treviokit` for production (a different name for development).
5. The app creates required unique/search/TTL indexes on its first database operation. Product name + size are case-insensitively unique; submission UUIDs use MongoDB's unique `_id` index. Atlas's replica-set deployment supports multi-document transactions; do not replace it with a standalone MongoDB instance.
6. Sign in locally, add a real product/size and retailer, and verify your intended workflow. MongoDB is the durable source of truth; Free-tier storage and connection limits still apply. Monitor capacity and arrange backups before business use.

See [Atlas Free cluster creation](https://www.mongodb.com/docs/atlas/tutorial/deploy-free-tier-cluster/), [Free cluster limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/) and [MongoDB Node transactions](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/).

## Backup and restore (Atlas Free)

Atlas Free does **not** provide the paid Atlas Cloud Backup facility. Permanence means durable database storage, not protection against accidental deletion. Schedule external backups and test restoration. Keep backups encrypted and access restricted because they contain retailer information and all transaction history.

1. Install [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/installation/). Use tools compatible with the source/destination MongoDB versions. Prepare a separate backup account with only the needed access.
2. Arrange a quiet maintenance window. Stop all app writes (pause access to the Vercel project and stop local instances); wait for in-flight transactions to finish. `mongodump` across collections is not a point-in-time snapshot while writes continue, and M0 does not provide the oplog snapshot workflow used by larger deployments.
3. Create a protected directory outside Git. Run the following, replacing placeholders, and enter the password at the prompt. The URI has no embedded password, so shell history will not contain it:

   ```sh
   mongodump --uri='mongodb+srv://CLUSTER.mongodb.net/' --username=BACKUP_USER --authenticationDatabase=admin --db=treviokit --archive=/SECURE_PATH/treviokit.archive.gz --gzip
   ```

4. Verify that the command succeeded. Encrypt and copy the archive to independent secure storage. Resume business access after the dump completes. Choose a schedule matching your acceptable data-loss window (for example, nightly and before maintenance); retain dated copies. Upgrade Atlas if you require automated continuous/cloud backups.
5. To test a restore, create a separate empty database/cluster, a destination user and its network access entry. **Never test restoration over the live production database.** Restore all collections and indexes (including submissions and history) with namespace mapping:

   ```sh
   mongorestore --uri='mongodb+srv://RESTORE_CLUSTER.mongodb.net/' --username=RESTORE_USER --authenticationDatabase=admin --archive=/SECURE_PATH/treviokit.archive.gz --gzip --nsFrom='treviokit.*' --nsTo='treviokit_restore.*'
   ```

6. Remove the restored `sessions` and `loginLimits` collections using Atlas Data Explorer before connecting the app, so backed-up sessions cannot authorize access. Use a fresh `SESSION_SECRET` too. Keep the `submissions` collection: it preserves duplicate protection.
7. Point an isolated local instance at `treviokit_restore`, sign in and verify product stock, invoice counts, original-price returns, retailer totals and linked exchange invoices. Record the restore time and backup date. Only then plan a production recovery with writes paused, a fresh empty destination, updated environment variables and a redeployment. Do not merge old backups into active data or use `--drop` casually.

Sources: [Atlas backup options](https://www.mongodb.com/docs/atlas/backup-restore-cluster/) and [MongoDB dump/restore guidance](https://www.mongodb.com/docs/manual/tutorial/backup-and-restore-tools/).

## Business rules and data

- Money is stored as integer poisha. Amounts support up to ৳10,000,000,000; quantities are whole numbers with at most 1,000,000 units per line. Stock adjustments require a reason and cannot make stock negative.
- Product name/size pairs are unique without case sensitivity. Archiving keeps inventory and history. Images use public HTTPS URLs; uploads are not supported.
- A sale requires an active retailer and unique product lines. Returns reference that retailer's original purchase, credit its original selling price and restore stock. Returned quantities cannot exceed purchased quantities less prior returns. An exchange references one original purchase; multiple original purchases can be handled as separate transactions.
- Invoice, stock, return links, payment snapshots, audit history and submission receipts commit together in a MongoDB transaction. Expenses, their audit history and receipt also commit together. Conditional writes and transaction retries handle concurrent stock/return requests; submission UUIDs prevent repeated writes and reject key reuse with different data.
- New invoices use sequential `TK-000001` numbers allocated atomically. Previously issued UUID-style numbers remain unchanged. Completed transactions and expenses have no edit/delete operation. Invoices retain product, size, price and retailer snapshots; original returned counters are internal bookkeeping.
- The recorded retailer balance is the sum of signed invoice net values minus recorded payments. Total payable includes previous due/credit plus the new transaction. Example: ৳750 previous due + ৳1,500 new net value = ৳2,250 payable; paying ৳2,250 clears both. Old debt is not counted again as revenue.
- Retailer settlement writes serialize concurrent checkouts. A changed balance rejects a stale checkout for review. Payments above combined total payable are rejected. Return credits reduce balances once; negative balances display credit. Standalone payment-only entries and actual refund disbursement tracking are not provided.
- Invoice tables show **Fully paid** for previous recorded invoices when current recorded due is zero. Status uses complete history even for filtered/paginated tables. When current due is positive, historic invoice due snapshots remain visible. Printed invoices preserve original checkout amounts. Older invoices without payment records remain **Not recorded** and are excluded from recorded balances.
- Audit history, expenses, products, retailers, invoices, return links, counters and submission receipts persist in MongoDB. Owner sessions and login attempt limits also live there. A cached MongoClient pool (maximum 5 connections per warm instance) and index initialization promise are reused on Vercel; instances can scale independently.
- One owner account; no registration, retailer accounts or employee management. Business pages/APIs require a valid owner session. Login/mutations verify `APP_ORIGIN`. Sessions expire after eight hours, use HTTP-only SameSite Strict cookies and require HTTPS in production. Logout revokes the session; changing `SESSION_SECRET` revokes all sessions. The shared login bucket allows ten attempts per 15-minute window.
- No ecommerce, shipping, suppliers, SKU, categories, cost prices or CRM. No seeded fake business transactions.

## A4 invoices

Open an invoice and click **Print / Save as PDF**. Select **A4**, **Portrait**, **100% scale** (or default scale), and disable browser **Headers and footers**. CSS sets 12 mm page margins. The invoice shows the retailer shop name, original purchase references, items/quantities, original-price return credit, net value, payments and checkout due/credit. Longer invoices continue on additional A4 pages with repeated table headings and intact item rows. The screen preview scrolls horizontally on small screens.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Invalid username or password | Use `OWNER_USERNAME` and the original password used to generate the hash; restart after editing `.env.local`. Disposable credentials work only on port 3110. |
| Operation could not be completed | Check all six server variables, Atlas database user/password, network access and cluster status. Server responses intentionally hide credentials and driver details. |
| Request origin is not allowed | Browser origin must match `APP_ORIGIN`, including scheme and port. Use the configured canonical domain. |
| Login fails in local `npm start` | Production cookies require HTTPS; use a local HTTPS proxy or `npm run dev`. |
| Retailer balance changed | Another checkout committed. Review refreshed previous due and submit again. |
| Invoice due differs from current status | Invoice amounts are checkout snapshots; tables also reflect whether the current retailer account is cleared. |
| Integration tests cannot start | Run the production build first; allow test MongoDB download and local ports; ensure port 3108 is free. |
